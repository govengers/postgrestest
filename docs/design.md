# govengers/postgrestest: design

Status: first version, 16.11.2026. Decisions are numbered `P1` onwards; a later change gets a new number, never a rewrite.

`govengers/postgrestest` is the PostgreSQL of govengers tests. Every library and service used to carry its own copy of an embedded-PostgreSQL harness (`internal/postgrestest` in jobs, auth, aikido, wide-event-logger and events, the `TestMain` of livewire's packages), and copies get no fixes: some kept their binaries in the OS temp directory and unpacked them on every CI run (30 to 60 s under `-race`), some swept a shared directory, one had a system-tar fast path the others lacked. This module is the one copy. Profile `library`, Apache 2.0, Go 1.26; govengers/standards apply.

## 1. The model

A **cluster** is one PostgreSQL a test binary uses: an embedded PostgreSQL 18 that only this process uses, or the server `POSTGRESTEST_URL` names (an external one, or the one the launcher started for the whole run). A **Server** hands out databases of one **template** on it; `WithTemplate` adds more templates on the same cluster. A **test database** is a copy of the template, made for one test and dropped after it.

```
TestMain ── Server.Main ── Close ─────────────┐
test ── Server.Pool / Database ── template ── cluster ── POSTGRESTEST_URL (launcher, external)
                     WithTemplate ┘                  └─ internal/instance: embedded PostgreSQL 18
cmd/postgrestest ── internal/instance ── POSTGRESTEST_URL ── go test ./...
```

## 2. Decisions

| ID | Decision |
|----|----------|
| P1 | One module. The root package imports pgx v5, embedded-postgres and the standard library only. `internal/instance` runs embedded servers (binaries, directories, locks, the orphan sweep) for the root package and the launcher `cmd/postgrestest`. The tests use testify and goleak; embedded-postgres' own `go.mod` already requires both, so they add no module to a consumer's graph. |
| P2 | API: `New(*Options) *Server` reads and starts nothing (LIB-004), not even the working directory; the first `Database(tb)` or `Pool(tb)` takes the scope (P6), starts the cluster and builds the template. `Database` returns the URL of a new database and registers its drop; `Pool` opens a pgx pool on it with pgx's defaults and closes it first. `Main(m)` returns a `TestingM` whose `Run` closes the cluster after the tests, so `goleak.VerifyTestMain(postgres.Main(m))` is the whole `TestMain`. `Close` is idempotent; afterwards `Database` fails the test (the error is unexported: only a test failure carries it, so no caller could match it). Helpers: `Statements(texts...)` (a Migrate that runs each text in a transaction of its own, as goose runs a file) and `FingerprintFS(fsys)` (a digest of an `embed.FS` of migrations). `testing.TB`, so benchmarks get databases too. |
| P3 | A database per test, copied from the template with `CREATE DATABASE ... TEMPLATE ... STRATEGY FILE_COPY` and dropped `WITH (FORCE)` in the test's cleanup. Rejected: a schema per test with the migrations applied per test (what the old harnesses did): the cost grows with the migrations, types, extensions and anything else outside a schema collide, and `search_path` tricks leak into the code under test. Measured on an M-series Mac with a 7.8 MB template: copy 19.5 ms and drop 9.3 ms with `FILE_COPY`; `WAL_LOG` (the default since PostgreSQL 15) copies in 24.5 ms; PostgreSQL 18's `file_copy_method = clone` is slower on APFS (24 ms); `wal_level = minimal` and a smaller `shared_buffers` change nothing. Database settings (`ALTER DATABASE ... SET`) are not copied by PostgreSQL; documented. |
| P4 | The template is built under a scratch name (`..._build`), marked `IS_TEMPLATE true ALLOW_CONNECTIONS false` and only then renamed into place, so the name only ever stands for a finished, marked template (a process that dies between two steps leaves a scratch database, which the next build drops): a session on a template makes every copy fail, and the flag keeps an accidental `DROP DATABASE` away. Builds of one package (same scope, P6) serialize on a session advisory lock; a session that cannot release it is closed. `Migrate` gets a `*pgx.Conn` on the scratch database; a connection it leaves open fails the rename (55006, after PostgreSQL's own wait of up to 5 s) with an error that says so, and the scratch database is dropped on every failure. |
| P5 | Fingerprints: a template's name carries a digest of `Options.Fingerprint`, so a server that outlives the test binary (one `POSTGRESTEST_URL` names) reuses a template of the same fingerprint. A fingerprinted template records its last use (`COMMENT ON DATABASE`, RFC 3339) every time a process starts using it; under the build lock, templates of the package unused for 24 hours are dropped. Rejected: dropping every other fingerprint of the package at once. Two runs of one checkout with different migrations at the same time then drop each other's template between two copies: a process caches its template name once and never re-checks, so every later copy fails with "template database does not exist" (seen with an earlier per-hash sweep). On embedded and launcher servers, which are new in every run, the fingerprint changes nothing: every run builds the template (tens of milliseconds for the govengers libraries; section 3). An empty fingerprint builds a template for this process only, dropped by `Close` (an embedded cluster takes it along anyway). |
| P6 | Names: `postgrestest_<scope>_<kind><suffix>`, at most 47 bytes. The scope is 12 hex digits of the SHA-256 of the working directory, which `go test` sets to the package directory: packages and checkouts never meet on a shared server. Kinds: `f` + 16 hex digits of the fingerprint's digest, `p` + random for a process template, `d` + random for a test database, `build` for the scratch. Identifiers are quoted with `pgx.Identifier`. |
| P7 | Embedded servers run embedded-postgres' binaries directly, `initdb` and `pg_ctl`, not the library's `Start`: a Unix socket in the server's own directory as the only address (`listen_addresses = ''`), so no free-port race between parallel test binaries and no TCP listener; `initdb --no-sync -A trust -E UTF8 --locale=C`; settings appended to `postgresql.conf` (no shell quoting through `pg_ctl -o`): `fsync`, `synchronous_commit`, `full_page_writes`, `autovacuum` and `jit` off, `max_connections = 500`, UTC; `pg_ctl start -w -t 60`, `pg_ctl stop -m immediate`, then the directory is removed (a stable one is emptied, P9). The library's `Start` costs the same (measured 0.48 to 0.51 s against 0.43 to 0.51 s from unpacked binaries), but it needs a TCP port, fsyncs in `initdb`, health-checks over lib/pq and removes its runtime directory first. The URL is `postgres://postgres@/postgres?host=<directory>&port=5432&sslmode=disable`: the port names the socket file, so `PGPORT` cannot redirect it, and spaces are `%20` (libpq and pgx read `+` as itself). A socket path above the platform's limit (107 bytes on Linux, 103 on macOS and the BSDs) puts the socket in `/tmp/postgrestest-<digest of the directory>` (stable, so the launcher's URL stays the same), which must be a directory of the current user that nobody else can enter: the server trusts whoever reaches the socket. Shortcut: the sweep leaves the short socket directory of a dead server behind. |
| P8 | Binaries: unpacked once per machine into `~/.embedded-postgres-go/postgrestest/postgres-<version>`, next to embedded-postgres' archive cache, which the govengers CI restores (go-library.yml), so a CI run starts from unpacked binaries. One process at a time unpacks, under a blocking `flock`, into a scratch directory it renames into place; scratch leftovers of killed unpacks are removed under the lock. The archive is unpacked with the system `tar` (5.4 s for the 33 MB archive in a `-race` binary on an M-series Mac, against 26.9 s for the library's pure-Go xz decoder plus a start). A missing archive is downloaded by an embedded-postgres start whose binaries directory sits in a read-only directory: the library fails right after the download, before its decoder runs (4.7 s with a download). Any surprise there (another library version, root) falls back to the library's own unpack-by-starting, the old harnesses' path. |
| P9 | Server directories: `i-<random>` for a test binary's own server, `run-<16 hex>` (the launcher's, P10). The owning process holds an exclusive `flock` on `<directory>/lock` for the server's lifetime; Go opens files close-on-exec, so the server never inherits it, and the kernel releases it when the owner dies however it dies. A new `i-` directory is created as `.new-<random>`, locked, then renamed, so the sweep never sees an unlocked directory of a live process. Every start sweeps: a server directory whose lock it can take has a dead owner; if `postmaster.pid` names a process whose command line (`ps -ww -o command=`) holds the data directory, it gets SIGQUIT (immediate shutdown) and up to 10 s to exit, then the directory goes. Stop and sweep remove an `i-` directory while they hold its lock (its name is never reused, so a second sweeper that takes the lock of the removed file finds nothing of anybody's); a `run-` directory and its lock file are never removed, only emptied, so the lock of the file is the lock of the directory and a claimer or sweeper can never hold the lock of a file that was replaced meanwhile. A stable directory that cannot be claimed, for any reason, falls back to an `i-` directory. Shortcut: `run-` directories are never removed, so one empty directory with its lock file stays for every checkout directory the launcher ever ran in, and every sweep lists them; remove those whose checkout is gone when they pile up. Directories of live processes, in this checkout or another, are never touched, and a reused process ID never gets a signal. Rejected: owner-PID files (PIDs are reused; the old harnesses needed the `ps` check for the owner too) and a sweep per package prefix (orphans of deleted worktrees would stay forever). Shortcut: a process killed between creating and renaming a `.new-` directory leaves it behind, empty. |
| P10 | `cmd/postgrestest command...` starts one server for a test run, runs the command with `POSTGRESTEST_URL` set, stops the server and exits with the command's status (2 without a command, 1 when the launcher itself fails). Its directory is `run-` plus a digest of the working directory: the URL, which `go test` counts among the inputs of every result it caches, is the same in every run of a checkout. A second launcher in the same checkout while the first runs gets an `i-` directory; its results miss the cache once. With `POSTGRESTEST_URL` already set it only runs the command. SIGINT and SIGTERM are forwarded to the command; the launcher outlives it to stop the server. A killed launcher's server is swept by the next start. |
| P11 | The Go test cache. `go test` hashes the environment variables a test binary reads (with their values) and the files it opens or stats inside the module root (by size and modification time); files outside the module, GOPATH and GOROOT are not checked (`cmd/go/internal/test`, `computeTestInputsID`). A package using this module reads `POSTGRESTEST_URL`, `HOME`, `PATH` (exec of `tar` and `ps`) and pgx's `PG*` variables, and touches files only below `~/.embedded-postgres-go`. It reads the working directory with `syscall.Getwd`: `os.Getwd` reads `PWD`, which `go test` sets to the directory it was started from, so a package started from another directory would rerun (the test of P2's lazy scope changes directory with `syscall.Chdir` for the same reason; `t.Chdir` reads `PWD`). Verified: an unchanged fixture package reports `(cached)` on the second plain run and on the second launcher run (end-to-end suite). `go run` puts GOROOT/bin in front of `PATH` for the command it runs, so a launcher started with `go run` and the same launcher binary started directly give different keys: a justfile should start it one way. This corrects an earlier note that the old harnesses' sweep of a shared temp directory defeated the cache: it is outside the module, so its listing is not an input; what made those CI runs slow was the unpack. |
| P12 | Tests: the root package's tests share one embedded server through `TestMain`; tests of attached servers point a cluster at it through an unexported address (no `t.Setenv`, so they run in parallel) and use scopes of their own, unique per run where a test counts template builds, so `-count=2` passes. `internal/instance` starts one stable server; the unpack path runs against a home directory with a small generated archive; sweep and orphan tests use fake directories and a shell whose command line holds the data directory. Not covered by unit tests: the download and the library fallback (network, and up to a minute under `-race`). The end-to-end suite runs `go test` on two fixture packages, plain and through the launcher, and checks one server per binary versus one per run, the cache hits, the exit status, a killed launcher's orphan stopped by the next run, and another checkout's server left running. |
| P13 | Embedded servers need a Unix-like system (`flock`, Unix sockets, `ps`); elsewhere the start fails with a message that points to `POSTGRESTEST_URL`, and attached clusters work. PostgreSQL refuses to run as root, so embedded servers do not run as root either. |
| P14 | Standards exceptions in `.govengers.yml`: DES-003 for the package variable that holds a package's Server (the documented usage, test code only), LIB-003 for `Main` writing a failed `Close` to standard error, the test binary's own output channel. |
| P15 | At most two `CREATE DATABASE` and `DROP DATABASE` statements of one test binary run at a time (a semaphore around the copy and the test's drop; template builds are already serialized by P4). Each forces checkpoints; unbounded, a binary ran as many at once as pgx's pool allows (the number of cores), and the parallel tests of several packages on one machine slowed the server to a fraction of its sequential rate: six packages of 40 parallel tests took 60 to 77 s, 6 to 7 s with the bound (Migrating.md); the review saw 18 packages through the launcher fail with drop timeouts. A copy waits for its slot as long as its test's context lives; the 30 s timeout of a drop starts when its statement may run, not while it queues. Two was the best of the bounds the review tried (four: 10 s for six packages). Rejected: `STRATEGY WAL_LOG` (34 to 48 s in the same load, review measurement) and a smaller pool for everything (a long Migrate would hold one of the two connections). |
| P16 | A failed template build is remembered on the Server, like a failed start: every later test fails at once with the same error instead of rebuilding and rerunning Migrate one after another (5 s each for a connection Migrate leaves open, enough to run a package with 120 tests into go test's timeout). A build that failed because its test's context ended is not remembered; the next test tries again. |

## 3. Not in v1, and when to add it

- Sweeping test databases and process templates that crashed test binaries left on an external server (their owner cannot be told from a live one by the name alone): when a long-lived shared server is in use.
- `.new-` leftovers of a crash during directory creation: by age, if they ever pile up.
- Options for server settings, the PostgreSQL version or the pool configuration: when a consumer needs one; `Database` returns a URL, so any pool configuration works today.
- A persistent data directory for the launcher to reuse templates across runs: measured start is 0.5 s and template builds of govengers libraries take tens of milliseconds, so it would buy little for the corruption and cleanup cases it adds.
- Windows support for embedded servers.
